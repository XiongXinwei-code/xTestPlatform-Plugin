# NI gRPC 设备插件

本插件通过标准 gRPC 调用运行在目标计算机上的 NI gRPC Device Server，提供 DAQmx 和 XNET CAN 的受控单次操作。服务端必须自行安装、启动并安装相应 NI 驱动；服务健康检查成功不代表设备或驱动可用。服务端及官方协议见 [NI grpc-device](https://github.com/ni/grpc-device)。本插件不安装服务端，也不调用服务器全局重置；所列功能不代表覆盖整个 DAQmx SDK。

## 步骤

- 公共：连接、关闭会话、断开连接。
- DAQmx：创建任务、配置 AI 电压、配置 AO 电压、配置采样时钟、启动任务、停止任务、读取模拟量、写入模拟量。
- DAQmx DI / DO：配置数字输入和输出、U32 端口位图读写。
- DAQmx Counter / Encoder：边沿计数、频率输入、脉冲频率输出与更新；角度和线性编码器配置；U32 计数与 F64 物理值读取。
- DAQmx Sync：采样时钟、隐式定时、数字边沿启动触发、信号导出，以及受控的共享参考时钟/采样时钟/时基/同步脉冲源和频率配置。
- XNET：创建会话、启动、停止、读取 CAN 帧、发送 CAN 帧、读取状态、读取属性、设置属性。

将完整插件文件夹放入平台 `Plugins/NiGrpc`，重新启动平台。连接名称和会话别名是平台表达式；每个创建步骤实际使用插件生成的唯一服务端名称。不同驱动、同一连接的会话通过不同别名区分。先创建对应的任务或会话，再使用同一连接名和别名调用步骤；收尾时关闭相应会话并断开连接。

## 表达式与 protobuf JSON

“请求 JSON”和“创建配置 JSON”是**求值结果为字符串的表达式**。例如要表达下面的 JSON，请在表达式编辑器填写 C# 逐字字符串 `@"{""physicalChannel"":""Dev1/ao0"",""minVal"":-10,""maxVal"":10,""unitsRaw"":10348}"`。字段具体含义见随源码提供的官方 `Protos/nidaqmx.proto` 与 `Protos/nixnet.proto`。不要在请求中指定 `task` 或 `session`，由插件按会话别名注入；不允许指定远端名称和初始化行为。

| 步骤 | 请求内容示意（以下是 JSON 值，不是可直接粘贴的 C# 表达式） |
|---|---|
| 配置 AO 电压 | `{"physicalChannel":"Dev1/ao0","minVal":-10,"maxVal":10,"unitsRaw":10348}` |
| 写入模拟量 | `{"numSampsPerChan":1,"autoStart":true,"timeout":1,"dataLayoutRaw":0,"writeArray":[1.2]}` |
| 配置 AI 电压 | `{"physicalChannel":"Dev1/ai0","terminalConfigRaw":-1,"minVal":-10,"maxVal":10,"unitsRaw":10348}` |
| 读取模拟量 | `{"numSampsPerChan":1,"timeout":1,"fillModeRaw":0,"arraySizeInSamps":1}` |
| 创建 XNET 输出会话 | `{"interfaceName":"CAN1","modeRaw":9}`；设备、数据库和会话模式应按现场 NI 配置调整。 |
| XNET 发送 CAN 帧 | `{"timeoutRaw":0.1,"buffer":[{"can":{"identifier":1796,"typeRaw":0,"payload":"AQI="}}]}`；`payload` 为 Base64，此例是 `01 02`。 |
| XNET 读取 CAN 帧 | `{"numberOfFrames":10,"maxPayloadPerFrame":64,"protocolRaw":1,"timeoutRaw":0.1}` |

XNET 输入与输出分别需要适合读或写的会话模式；是否允许同一接口创建多个会话依硬件及服务端而定。成功提交帧不代表应用层响应或物理设备状态，接收须使用独立读取步骤。写入数组长度须等于实际通道数乘每通道样本数。响应为 protobuf JSON；可选配置完整字符串变量路径，如 `Locals.ResponseJson`。64 位整数在 protobuf JSON 中可能表示为字符串；默认零值和空数组字段可能被省略，缺省值按官方 proto 解读。

## DAQmx 数字量、计数器、编码器与同步

新增的 17 个步骤各自提供预填的请求表达式和独立编辑器。请求与结果保持字符串，平台助手可读取、设置完整内容；通道、终端、范围等需要按实际设备修改。请求先经过本地官方协议和参数校验，再注入当前任务，不允许指定其他任务句柄。数字及计数器写入会先查询实际虚拟通道数；取消或执行代次退出后，预查询不得继续提交旧输出。

数字 U32 数组的每项是一个虚拟通道的端口位图，通道数取决于 `lineGroupingRaw`，不等于物理线数。端口位图保留物理位位置，例如 `Dev1/port0/line4:7` 全部为高对应 `0xF0`，不压缩成 `0x0F`。`fillModeRaw` / `dataLayoutRaw` 为 0 时按通道排列，1 时按扫描排列；两通道各两样本的顺序分别是 `[通道0样本0, 通道0样本1, 通道1样本0, 通道1样本1]` 和 `[通道0样本0, 通道1样本0, 通道0样本1, 通道1样本1]`。

读取结果保留 `readArray` 与实际 `sampsPerChanRead`，不会把请求容量冒充实际样本数。数字写入返回 `sampsPerChanWritten`；计数器频率写入返回 `numSampsPerChanWritten`。`ReadCounterU32Ex` 用于计数，`ReadCounterF64Ex` 用于频率/编码器位置，单位由通道配置决定；角编码器 `pulsesPerRev` 填实际每转脉冲数，不重复乘 X4。脉冲更新 `WriteCtrFreq` 要求频率和占空比数组同长，频率大于 0，占空比严格介于 0 和 1，默认不自动启动。

硬件同步需要可用共享时钟/时基、触发和物理路由。配置顺序为：创建各任务 → 配置通道 → 配置时钟/隐式定时及触发/信号导出 → 必要时预装输出数据 → 先启动等待触发的从任务 → 最后启动主任务。多个依次执行的 gRPC `StartTask` 不能证明采样同步。Sync 的属性步骤只允许所列时钟源和频率白名单，不开放任意 DAQmx 属性；具体设备不支持的路由或模式由 NI 返回错误。停止任务不删除会话，独立关闭会话步骤仍负责 `ClearTask`。

实现依据为 NI 的 [官方 DAQmx proto](https://github.com/ni/grpc-device/blob/main/generated/nidaqmx/nidaqmx.proto)、[数字输入示例](https://github.com/ni/grpc-device/blob/main/examples/nidaqmx/digital-input.py)、[计数器输出示例](https://github.com/ni/grpc-device/blob/main/examples/nidaqmx/counter-output.py) 和 [共享时基及启动触发示例](https://github.com/ni/grpc-device/blob/main/examples/nidaqmx/dsa-shared-timebase-and-trig-analog-input-and-output-aio.py)。本次未变更随项目固定的官方 proto。软件假服务验证覆盖协议和生命周期，不代表实际硬件线路、输出或同步精度已经验证。

XNET 启动和停止支持接口级 scope；修改波特率或终端电阻也作用于物理接口，可能影响该接口上的其他会话。应按实际共享关系配置。

XNET 读取/设置属性目前仅支持 NI 官方协议中 CAN 波特率、CAN FD 波特率和终端电阻的 32/64 位属性（ID：1048598、1048615、1048613、152043542、152043559）；状态读取仅支持当前时间、会话和已核实的 CAN 状态 ID。其余方法、协议和属性未纳入首版。具体字段和所需类型以固定的官方 proto 为准。

## 超时、取消与安全边界

`TimeoutMs` 是单个步骤的客户端等待期限。RPC 超时、连接丢失或用户中断不能证明服务端的驱动调用已经退出或设备动作没有发生。发生结果未知时，插件保留错误及远端会话名称，不自动重发写操作或冒险清理其他客户端资源；应先确认远端状态后，再由用户决定恢复方法。关闭过程中出错也不会伪称远端资源已经释放。

调用方取消会立即将取消状态转发到独立的 gRPC 令牌，下游回调在后台执行；已提交调用的真实退出和首次取消回调仍由原会话跟踪。健康检查也使用独立令牌及软超时。远端 Clear 已响应但本地回调尚未退出时，会保留会话归属并报告等待未完成。

显式关闭会话步骤在排队后和提交 Clear 前检查原执行代次；作用域已经退出时不再主动提交旧的关闭请求。连接资源自动收尾仍独立执行，已提交但未确认的 Clear 保持结果未知。

同一平台进程、同一 NiGrpc 加载实例的执行代次共用一个保守协调域：另一代仍持有连接、活动步骤或真实调用时，新一代步骤按自己的 `TimeoutMs` 等待；确认远端结果未知时，新设备操作直接报隔离错误。为了避免 DAQ 通道未确定和服务器地址别名绕过隔离，该策略也会使不同设备的并行运行互相等待；已确认关闭且无活动任务时释放协调域。原代次的关闭与资源自动收尾仍独立执行。重启进程不会证明远端调用已经退出；其他插件、进程和客户端不受本协调域约束。当前不提供强制解除未知隔离的步骤。

单个步骤取消不会自动关闭同一运行中其他连接。被取消步骤的后台工作未退出时，普通设备操作等待收尾，关闭操作仍可进入；若该步骤已提交设备请求且远端结果未知，整个协调域继续隔离。连接关闭在等待已有会话调用时超时，并不意味着 Clear 已提交：后台会继续持有通道与所有权，待已知调用真正退出后再清理；调用或 Clear 已提交但结果未知时则不会自动重试。创建操作的收尾也被跟踪，即使其会话别名已移除，只有本地关联任务退出后才能关闭通道。

表达式求值也计入步骤期限；超时结束等待不表示后台表达式已经退出，表达式应避免产生设备动作等副作用。

当前会在会话队列等待后、驱动预查询前后检查执行作用域；但该检查与 gRPC 实际创建调用并非原子操作。如果作用域在检查后、提交前回收，仍存在旧请求进入服务端的并发窗口。结果写入变量也存在检查与写入之间的窗口。不能将这些检查视为硬件安全互锁；未完成现场验证前，不应依赖它们保证中断后设备绝不动作。

支持明示 HTTP 或使用系统信任证书的 HTTPS，当前版本不支持配置客户端证书（mTLS）；仅在网络和服务端安全策略允许时使用。禁止将凭据写入服务地址。离线假服务测试和构建不能替代 NI Device Server、硬件、台架中断重跑及物理输出验证。

## 参数写入校验

平台助手与页面使用同一份强类型设置。插件在参数转换及保存前校验：未知或重复字段、类型不符、未定义枚举、不允许的 null、非有限数和赋值后被忽略/改写的值均明确报错，并保留原步骤数据。对象数组需提交完整 JSON 数组；请先读取全部当前项再修改，避免替换时遗漏配置。表达式文本不会在保存时执行，依赖变量或设备的有效性仍由步骤校验与执行处理。
