# 平台插件契约与错误日志统一改造方案

> 状态：平台/SDK 增量阶段已由平台工程实施，本插件工作区已接入 SDK 1.2.8 并完成本期迁移；严格状态校验及后台故障上报仍待独立交付。SDK 1.2.7 不具备新增 API。
> 技术基线：.NET 8；当前插件工作区引用 `xTestPlatform.StepEditor.SDK` 1.2.8。平台实施记录见 §11，插件记录见 §12。
> 依据：[步骤插件开发手册](../xTestPlatform_StepPlugin_Development_Guide.md) §2.4、§2.5、§6.1、§13.4、§13.5。

## 1. 改造目标与结论

采用“**契约提供统一结果工厂，引擎统一记录最终错误，插件补充业务上下文**”的方案。

不要求每个插件实现新的日志接口，不在每个执行器内重复编写错误日志，不通过新增日志 NuGet 包解决问题。

本期目标：

1. 普通步骤插件正常执行返回 `Completed`，执行有问题返回 `Error`，用户主动取消返回 `Aborted`。
2. 插件每次执行返回 `Error` 时，引擎保证产生一条对应的 Error 级最终错误日志。
3. 插件抛出未捕获异常时，引擎转为 `Error`，保留异常链与堆栈并统一记录日志。
4. 日志主消息与步骤结果中的错误消息一致；诊断详情可展开查看，不混入报告正文。
5. 兼容已有结果对象的构造和序列化方式，分阶段迁移旧插件。

**范围边界：**本规则针对普通插件执行结果，不删除平台的测试判定能力，也不修改内置判定步骤、聚合结果和历史报告中的 `Passed` / `Failed` 语义。

## 2. 当前问题与平台侧收益

插件工作区的只读审查发现：

- 10 个执行项目、95 个执行器普遍直接构造 `ExecutionResult`，没有统一的最终错误日志出口。
- 未发现插件显式调用 `LogLevel.Error`。返回 `ErrorInfo` 不等于已经输出错误日志。
- `ErrorInfo.FromException` 已约定保留异常链和堆栈，但部分调用仅传递字符串，详情在进入引擎前已经丢失。
- 大量执行器在 `try` 外读取或反序列化配置，配置损坏可能绕过插件自己的错误处理。
- 后台采集或周期发送故障不一定经过已经结束的启动步骤返回值。

在引擎边界统一处理后，现有的直接 `new ExecutionResult`、共享 helper 提前返回和未捕获异常都可以进入同一个最终错误日志出口。业务上下文缺失、底层已丢弃的异常和后台故障仍需插件侧后续改造。

## 3. 职责分工

| 层次 | 应承担的职责 | 不应承担的职责 |
|---|---|---|
| `ExecutionResult` 结果工厂 | 构造状态、错误消息、详情、错误码与实际值 | 调用日志、访问执行上下文、计算步骤耗时 |
| `ErrorInfo.FromException` | 保留完整异常链与堆栈，支持自定义中文主消息 | 自动推断设备、节点、地址或重试次数 |
| `IStepExecutor` 插件实现 | 执行业务，提供操作上下文，输出过程日志，返回结果 | 重复记录即将作为最终结果返回的同一个错误 |
| 引擎插件执行边界 | 兜底捕获异常、补齐非法结果、记录最终错误日志、发布结果 | 把测试值不符合期望直接判为执行错误 |
| 后台任务管理 | 上报任务运行期间的故障，并保留任务状态 | 事后改写已经发布的启动步骤结果 |

## 4. 契约改造：新增结果工厂

### 4.1 推荐 API

实际 SDK 1.2.8 使用 `xTestPlatform.Core.Models.ExecutionResults` 静态类提供以下方法。由于已有 `ExecutionResult.Error(string, int)`，依兼容要求没有在原类型新增同名等价入口；§11 已记录该决策。

```csharp
public static ExecutionResult Completed(string? value = null);

public static ExecutionResult Error(
	string message,
	string? detail = null,
	int errorCode = 0,
	string? value = null);

public static ExecutionResult FromException(
	Exception exception,
	string? message = null,
	string? value = null);

public static ExecutionResult Aborted(string? value = null);
```

**本期不新增 `IStepExecutor` 必须实现的成员，不改变 `ExecuteAsync` 签名，不要求在 `IExecutionContext` 上新增日志接口。**现有 `Log(LogLevel, string, string?)` 足以记录最终错误。

如果平台实际类型已有同名成员冲突，可将上述方法放入独立的 `ExecutionResults` 静态类；不要为了工厂方法删除已有公开成员。具体方案在平台主工程中统一后再发布，避免 SDK 同时出现多套等价 API。

### 4.2 工厂行为要求

所有工厂方法：

- 每次返回独立的 `ExecutionResult`、`StepResult`；错误工厂每次创建独立的 `ErrorInfo`，不得缓存可变结果对象。
- 不记录日志、不读取 `IExecutionContext`，不推断步骤名称或执行地址。
- 保持当前结果默认路由：`Signal = ExecutionSignal.CollectResult`，不改变其他默认字段。
- 返回后允许调用方继续填写现有的 `Unit`、边界、条件等字段，不改变其数据结构。
- 不设置伪造的执行耗时、循环号或步骤元信息；这些字段按现有引擎机制处理。
- 未提供 `value` 时保持当前 SDK 的默认值约定，不借本次改造改变序列化的空值语义。

| 方法 | 结果要求 |
|---|---|
| `Completed` | `Status = Completed`，`Error = null`，保留实际值；不代表测试通过 |
| `Error` | `Status = Error`，创建 `ErrorInfo`，原样保留有效消息、详情、错误码和实际值 |
| `FromException` | `Status = Error`，调用现有 `ErrorInfo.FromException`，不只是复制 `exception.Message` |
| `Aborted` | `Status = Aborted`，`Error = null`；不主动记录 Error 日志 |

参数约束：

- `Error` 的 `message` 为 `null`、空串或全空白时，按参数错误抛出 `ArgumentException`；调用位置在插件内时由引擎兜底捕获并报告。
- `FromException` 的 `exception` 为 `null` 时抛出 `ArgumentNullException`。
- `FromException` 未提供有效中文消息时，提供中文兜底主消息“步骤执行异常，请查看诊断详情”，并保留原异常详情。
- `FromException` 不自行把 `OperationCanceledException` 转为 `Aborted`。取消原因需要由调用层根据用户取消令牌判断。

### 4.3 `ErrorInfo` 要求

优先复用现有 `ErrorCode`、`Message`、`Detail`，本期无需增加必填字段或改变已有成员类型。

| 字段 | 规范 |
|---|---|
| `Message` | 面向用户的简洁中文：操作对象、失败动作、原因；不要拼接整段堆栈 |
| `Detail` | 异常链、堆栈、协议返回、具体失败项等诊断信息；允许为空 |
| `ErrorCode` | 有明确设备、HTTP 或协议错误码时填写；没有时保留现有默认值 |

`ErrorInfo.FromException(ex, message)` 必须尊重调用方提供的非空主消息，并保留完整外层异常、内层异常及堆栈，不能只取 `GetBaseException().Message` 而丢弃包装层信息。若当前实现已满足，不重复改造。

参数错误或设备否定响应可能没有 .NET 异常，不要求制造异常或伪造堆栈。此时重点是提供足够的设备、地址和协议上下文。

### 4.4 插件调用示例

```csharp
return ExecutionResult.Completed(actualValue);

return ExecutionResult.Error(
	"节点 3 的 SDO 读取被设备拒绝",
	detail: "Index=0x2000，SubIndex=0，AbortCode=0x06020000",
	value: "0x06020000");

return ExecutionResult.FromException(ex, "读取串口 COM3 失败");
```

以上工厂调用均不输出日志，由引擎消费最终结果时统一记录。

## 5. 引擎改造：唯一最终错误出口

### 5.1 实施位置

在平台主工程中定位 `PluginStepHandler` 或实际负责调用 `IStepExecutor.ExecuteAsync` 的边界。该类型名称来自手册，实际文件路径及调用链以平台源码为准。

先梳理已有的异常日志、步骤完成事件、结果收集与日志订阅路径，确认是否已经根据 `ErrorInfo` 记录日志。应复用或合并已有出口，而不是在多个位置各补一条。

普通插件的执行路径建议收敛为：

```text
进入一次插件执行尝试
	→ 在兜底 try/catch 内创建或取得执行器并调用 ExecuteAsync
	→ 得到插件返回结果，或将异常转换为结果
	→ 按现有路由区分普通结果与控制信号
	→ 规范化普通插件结果并补齐步骤元信息
	→ 若为 Error，输出一次最终错误日志
	→ 按原有机制发布/收集结果
```

兜底范围应覆盖平台负责的配置读取、执行器创建及实际调用；不能只包住 `await` 而让前置解析异常逃逸。不要借此把插件加载失败、整个平台启动失败等其他生命周期错误都伪装成某个步骤的执行结果。

### 5.2 异常与取消映射

| 情况 | 处理方式 |
|---|---|
| 插件正常返回 `Error` | 保留插件的错误码、消息、详情和实际值，补齐必要元信息，统一记日志 |
| 插件抛出普通异常 | 用 `FromException` 转为 `Error`，中文主消息包含步骤名称或类型 |
| 抛出取消异常，且用户取消确实已触发 | 返回 `Aborted`，不作为执行错误记录 |
| 超时导致取消，用户未主动取消 | 返回 `Error`，说明超时，保留原异常 |
| 插件返回 `Completed` | 正常发布结果，不产生最终错误日志 |

**不能只检查传给插件的链接令牌是否取消来区分用户取消和超时。**链接令牌可能同时包含用户停止、步骤截止时间等来源；应以引擎掌握的原始用户取消令牌或已记录的停止原因判断。

插件已经返回 `Error` 后，不得因为同时发生取消就无条件将该结果改为 `Aborted`；取消映射主要用于捕获取消异常的路径，避免掩盖已明确返回的错误。

### 5.3 非规范结果兜底

| 非规范情况 | 规范化要求 |
|---|---|
| 返回的 `ExecutionResult` 或 `StepResult` 为 null | 转为 `Error`，说明“插件未返回有效的执行结果”，带步骤类型等上下文 |
| `Status = Error`，但 `ErrorInfo` 为 null | 补充“步骤执行失败，插件未提供错误描述” |
| `Status = Error`，但消息为空白 | 补齐中文兜底消息，保留已有详情、错误码和实际值 |
| 普通插件最终结果为 `Passed` / `Failed` | 严格规范启用后转为契约错误，提示插件应返回 `Completed` / `Error`；详情保留原状态，不悄悄解释为设备失败 |
| `Completed` 却附带非空 `ErrorInfo` | 视为契约不一致，严格规范启用后转为 `Error`，保留原错误信息并说明冲突 |

最后两条只用于明确识别的普通插件结果，**不能全局替换内置判定步骤和报告结果中的状态**。`Skip`、`StartStep`、`NextStep` 等控制信号继续走现有路由，不在本期强制改写为普通完成或错误结果。

`None`、`Running` 等非终态的校验应与平台现有控制流程核对后实施，不在未核实路由语义时一律改成 Error。

### 5.4 最终错误日志规范

规范化结果为 `Error` 后，调用已有日志 API：

```csharp
context.Log(LogLevel.Error, error.Message, error.Detail);
```

要求：

- 日志主消息与规范化后的 `ErrorInfo.Message` 一致；步骤名称、地址等关联信息优先通过现有结构化元信息携带。
- 详情放入 `detail` 参数，与 `ErrorInfo.Detail` 一致，不把堆栈拼进主消息。
- 不手写 `[Error]` 前缀，不自行生成时间戳。
- 按现有日志机制进入 LogMonitor 与运行时日志文件；报告正文仍只显示主消息，保持现有详情展示约定。
- 日志基础设施异常不得覆盖原始步骤错误；沿用平台已有的日志失败处理机制，不在本次另造日志系统。

### 5.5 去重边界

“只记一次”是指**同一次执行尝试的一份最终错误结果只输出一条最终错误日志**：

- 插件返回 Error 和引擎 catch 的结果，最终走同一条结果处理路径。
- 不在 catch、最终结果收集器、步骤完成订阅者中重复记录同一份最终错误。
- 不能只按步骤地址或消息文本去重：循环、重试、子序列和并行运行会重复执行同一步骤。
- 若已有运行实例/步骤尝试标识，复用该标识；不要为了去重新增必须序列化的 `ErrorLogged` 字段。
- 重试过程日志与最终错误日志不是同一事件，可保留重试 Warn；实际每次重新执行的失败尝试不是重复日志。
- 历史结果加载、报告回放或 UI 刷新不得触发新的运行时错误日志。

旧插件可能自行记录相同 Error，不能靠匹配字符串自动消除。应明确迁移插件与宿主的日志责任，必要时将此作为发布说明中的已知重复来源。

## 6. 后台任务边界：另行设计，不阻塞本期

结果工厂和执行边界只能覆盖插件本次调用，不能捕获启动步骤返回后的后台采集、周期发送异常。

本期要求：

- 文档明确此边界，不承诺“加了工厂方法就覆盖所有后台异常”。
- 后台任务继续保留自身的过程日志和资源清理职责。
- 不把已经完成并发布的启动步骤结果事后改为 Error。

后续可单独设计任务故障上报能力，至少包含运行实例、任务标识、所属步骤及 `ErrorInfo`。任务管理层负责记录故障并保存状态，读取/停止步骤可返回该任务的已知错误。

故障上报不应通过擅自新增变量或拼接隐式变量路径实现，也不能只发一个没有消费者的自定义事件就认为任务状态已可靠保存。本期不直接为 `IExecutionContext` 添加新的必需接口成员。

## 7. 兼容与发布策略

### 7.1 API 与序列化兼容

- 保留现有 `IStepExecutor.ExecuteAsync`、`ExecutionResult` 构造方式、属性及 setter。
- 不删除或重排 `TestStatus` 枚举成员，不改变已发布枚举数值。
- 不新增 `Warning` 步骤执行结果；`StepSettingError.Warning` 和 `LogLevel.Warn` 保持原义。
- 不改 Setting 格式、版本、变量路径和插件 DLL 命名；工厂方法只是新的构造入口。
- 原有直接构造结果的插件仍可被统一日志入口处理，无需全部改成工厂方法后才能受益。

### 7.2 行为兼容与部署顺序

新增静态方法属于增量 API，但“拒绝普通插件返回 Passed/Failed”是行为约束，**不能宣称对所有旧插件完全无影响**。

建议分阶段发布：

1. **平台/SDK 增量阶段**：增加结果工厂、异常兜底与最终错误日志，验证并消除宿主内部重复日志出口。
2. **插件迁移阶段**：审计旧插件状态，正常改 Completed，执行问题改 Error，补齐业务上下文并移除重复的最终错误日志。
3. **严格规范阶段**：插件清单审计完成后启用普通插件状态一致性校验；若需要过渡开关，必须有明确的开启条件和移除计划，不静默永久兼容错误状态。

本工作区已引用 SDK 1.2.8。部署前须确保平台主程序与 SDK 所携带的 Core 契约一致；实际最低宿主版本由平台发布流程确认，不根据 SDK 版本号推断。

使用新工厂编译的插件需要包含相应方法的新平台 Core；新 SDK 插件放入旧平台会有缺失方法风险。按“先平台，后插件”的顺序部署，不在各插件私有目录放入相互冲突的 Core 版本。

回退时恢复相互匹配的平台与插件版本，不能只将平台降级而继续使用依赖新工厂的插件。

## 8. 插件侧后续迁移重点

平台统一入口解决日志覆盖，但不能恢复插件已经丢弃的信息。建议随后按以下顺序补齐：

| 范围 | 后续迁移内容 |
|---|---|
| CANopen | SDO Abort、超时保留原异常；补充节点、Index/SubIndex 或 COB-ID |
| UDS | NRC 中文说明与数值码；补充 SID/DID、TX/RX ID 和实际 P2/P2* 等待值 |
| 刷写 | 明确擦除/下载/传输/校验阶段；将详细诊断放入 Detail，保留实际 Value |
| HTTP/SOAP | 超时传递原异常；补充请求方法、脱敏 URL 和超时值 |
| OPC UA 批量写入 | 列出失败项 NodeId、StatusCode，而不是只有失败数量 |
| LabVIEW | 底层包装层保留原异常或 InnerException，不只传 `ex.Message` |
| 其他插件 | 用中文主消息补齐连接、设备、通道、寄存器、命令序号等上下文 |

密码、Token、密钥、认证头以及敏感请求/响应数据不得直接写入日志或 Detail。脱敏责任不能因为新增错误工厂而省略。

## 9. 验收测试清单

建议使用假的执行器、日志接收器和执行上下文做自动化测试，无需连接真实设备；具体测试框架沿用平台现有工程。

### 9.1 工厂与信息保留

- [ ] 四种工厂的状态、实际值、默认信号正确，每次返回独立对象。
- [ ] `Error` 保留消息、详情、错误码；非法空消息按约定处理。
- [ ] `FromException` 保留外层异常、内层异常及堆栈，尊重自定义主消息。
- [ ] 非异常业务错误可使用空 Detail，不制造堆栈。
- [ ] 工厂自身不产生任何日志。

### 9.2 引擎错误出口

- [ ] 直接构造的 Error 与工厂构造的 Error 均恰好输出一条最终错误日志。
- [ ] 日志等级为 Error，主消息与 ErrorInfo 一致，日志详情与 Detail 一致。
- [ ] 返回 null、缺 ErrorInfo、空白 Message 都有可理解的中文兜底结果与日志。
- [ ] 执行器创建、配置解析或反序列化抛出异常时，也进入统一错误出口。
- [ ] HTTP 等超时保留原异常；非用户取消不能返回 Aborted。
- [ ] 用户取消返回 Aborted，不产生最终错误日志。
- [ ] 已返回 Error 不因同时发生取消而被无条件覆盖。
- [ ] Completed 不产生最终错误日志。

### 9.3 路由、并发及兼容

- [ ] 内置判定步骤与历史报告的 Passed/Failed 不受普通插件状态校验影响。
- [ ] 控制信号仍按原有机制路由，不被错误规范化吞掉。
- [ ] 循环、重试、子序列和并行运行相互独立，不因同名步骤或相同消息丢日志。
- [ ] UI 刷新、历史结果加载和报告回放不新增运行时日志。
- [ ] 旧插件直接构造 Completed/Error/Aborted 的行为不变；无需新接口实现。
- [ ] 严格规范启用时，普通插件返回 Passed/Failed 的契约错误可定位到具体插件。
- [ ] 原有结果字段、枚举数值与序列化兼容性测试通过。
- [ ] 新 SDK 插件与平台运行时 Core 版本匹配；回退演练使用成套版本。
