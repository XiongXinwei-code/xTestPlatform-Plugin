# 全插件生命周期机制复核与三轮勘误

## 任务等级与基线

- L3：跨十插件、共享资源并发、超时取消与设备生命周期。以干净 `260f749cd6d78af9ecf2fcfd9b3a1d30ab6e4273` 为起点，上一轮 1946 项通过只作已有基线，不宣称本轮已验证。
- 2026-10-26 fetch 后 master 为 `5351a0a9d66594455b292fe65308303488a07537`，本地与远端开发手册 blob 均 `9ca9f70eb10a14cd9a931bcc3fe7fe5995da93d0`。
- 用户要求解释原理、查同类机制、修复、三轮勘误；此前明确“暂无，先完成软件验证”。本轮仍不连接真实设备、不写实际平台插件目录、不新增自动重连/停机字/输出复位。

## 核查的不变量

一次步骤的前台等待结束、原调用方取消、owner 退出、实际原生调用结束、句柄释放是不同事实。停止/回收应立即冻结本 owner 的新提交，结束已无效的前台等待；实际 I/O、取消回调及资源释放仍必须被跟踪到完成。新运行只等旧资源真实释放，不能受旧前台等待或旧诊断错误永久锁住，也不能强清未知 I/O 制造重跑成功。

## 能力与审查安排

- 当前 Codex 使用 ECC planner/architect 方法制定本计划，依据真实调用链决定是否修改共享机制，避免每个执行器继续复制补丁。
- 独立只读审查分为 CAN/CiA402/LIN、NI/OPC UA/VISA、网络/HTTP/Modbus/串口三组。主线程负责 Shared、SDK 资源回收合同、复现和集成。首阶段各组不改文件、不构建、不运行设备；并行实施须另行明确独立文件与构建窗口。
- 核心行为用 ECC TDD 方法先保留屏障/fake/真实 SDK RED，再改最小实现和 GREEN。C# reviewer 与 silent-failure-hunter 检查错误传播、共享状态、等待/真实退出的分离；非作者对最终变化复审。
- security-review 只检查本次实际跨信任边界的输入/路径/日志差异；同一构建内私有共享类型原子演进，不额外引入跨消费者契约工具。步骤 SDK 公共接口和序列字段保持兼容。
- 最后按 verification-loop 做最终源码对应的构建、定向/完整测试、UTF-8、身份、依赖及产物指纹。WPF 有变化才复测受影响实际控件；没有安全平台工程时不得把组件/fake 结果当宿主或硬件 E2E。

## 阶段与验收

1. 第一轮机制审查：确认 1021 项自有产品源码基线及当前入口/owner/后台任务/退出链，列出实际本轮复核与复用范围。重点验证 SDK 回收不取消 step token、已排队和已提交的非合作 I/O、关闭重试、旧执行晚返回和物理资源重用。
2. 复现与机制设计：用确定屏障验证假设。首个候选问题为 Shared PendingIoGate 的 closing 仅冻结准入却没有唤醒已等待者，自定义 CAN/HTTP 等待可能有同构；目前只是待验证假设。依据测试选择共用的 owner 关闭信号/前台等待原语，绝不以取消 Task 或放宽期限冒充真实退出。
3. 第二轮修复与独立复审：先在共享原语封闭根因，再逐个核对十模块接入、原 caller→Aborted 与内部回收→中文 Error 的分类、配置预算、未决 I/O 及真实释放。新增问题重测后复审，不用改变安全合同迎合夹具。
4. 第三轮最终验证：冻结产品源码，运行相关完整回归及十核心/十 UI 构建，检查 120 步骤身份/旧序列兼容、私有 CAN 一致、UTF-8/源码与 PE/PDB。新输出根目录 `artifacts/Release/2026-10-26-lifecycle-mechanism/Plugins`，不覆盖上一交付；证据 `artifacts/lifecycle-mechanism-20261026/`。
5. 文档/提交：写明已确认根因、同类路径、机制改变的理由、各轮真实失败和修复结果，以及未验证边界。中文 Conventional 提交包含原因/改动/验证和协议/硬件回退；只本地提交，不推送/部署，保留旧备份。

## 架构取舍与复现后的修正

- 优先在共享 owner 原语区分前台退出信号与实际 I/O，避免仅给更多执行器加 catch 或重试。信号不得调用任意 native/日志回调，也不得清空真实任务引用。
- 需要覆盖排队取消后的 semaphore 归还，不能因前台先退出泄漏锁或允许关闭和旧 I/O 并行使用句柄。
- 不把用户超时当资源生命周期，不把 SDK Cleanup 当用户主动取消；后台可能永久不退时，前台可返回但资源必须隔离。
- 不重写 CiA402 状态机，不代轴步骤关闭父 CAN，不改变有序 RPDO→SYNC、反馈时间真实性或设备停稳标准。

### 已执行的第一、二轮

- 第一轮保留真实 RED：Shared 活动/排队等待与同步诊断 3/4 失败；Modbus 纯批次延时在 SDK 两种清理后均不能及时结束；CAN/LIN/CiA 的长等待、VISA 原生取消、OPC 消费停止、Serial 建立补偿亦有各自屏障失败记录，均在 artifacts/lifecycle-mechanism-20261026。编译错误、夹具误用和未运行的假设不计 RED。
- 单纯增加 owner stop 仍覆盖不到尚无 owner 的表达式/初始化/纯延时，因此全部 120 步骤的实际工厂使用私有 ExecutionScopedExecutor，SDK IResourceRegistry/IStepExecutor 公共合同不变。ExecutionEpoch 独立通知 SDK 回收，旧异步续体保持原代次，不能捕获新执行资源续跑。
- 非作者复审反证了“只在 SDK 先清理后才结束等待”的不完整设计：caller 先停止而清理等待步骤返回时，非合作表达式仍卡住。已新增确定 RED，再使用每步独立 StepLifetime；它先标记旧步骤退休，再仅对本步新 owner 或精确操作代次请求快冻结，真实 I/O/回调/句柄依旧由原 owner 持有。成功步骤解除这些短期关联，避免重现绑定后旧 step token 误杀长寿命资源的问题。
- Own 只登记完成构造且尚未提交 I/O 的精确 owner；执行级连接池不是某一读取步骤的私有资源，不对整个复用 pool 绑定 Own。既有半双工事务使用可解除的 OwnOperation，在成功准入后才登记，结果/取消处理后解除；未准入的排队取消不能关闭别的事务。
- 手册 §13.4 的“明确 Error 不因并发取消被覆盖”有单独 RED/GREEN；退出请求本身失败时把清理错误并入原 Detail，仍保留原 Error。尚未消费的晚到 Error 单独后台观察，避免 finally 完成竞态和敏感载荷日志。
- 非作者审查继续发现 caller.Cancel 可同步级联原生回调，以及原生本体返回不等于取消回调退出。VISA/CAN/LIN/CiA 用各自私有取消桥把取消请求、真实回调完成归入原事务；关闭不能越过回调释放 gate/句柄。CAN 已完成历史失败后的重复 Dispose 日志也改成后台观察。
- 收口复审又关闭三组交错：OPC 消费在同锁封闭取消入口后才捕获回调完成 Task；VISA 双失败详情不丢失，慢报告不计入真实 I/O；独立清理任务不继承已退休普通步骤的执行上下文。Shared 与 CiA 均有确定 RED/GREEN，CAN 未成功返回的启动被取消后仍按精确 owner/代次执行已配置停机，不先取消 worker 跳过收尾。
- 长批次的已完成 OwnOperation 会精确注销，HashSet 避免累积及线性重复查找；2,000 次已完成操作的回归只保留一个当前长 owner。DoIP 的完整 NRC 返回 Error 后仍能在健康会话再次完成请求，证明普通业务 Error 不误关已完成事务。
- root Shared 与网络/HTTP/Modbus由另组作者只读复审；NI/OPC/VISA与CAN/LIN/CiA交叉非作者复审。审查发现项逐条重测，模块回归通过只算该次源码，不替代最终冻结后全量验证。
