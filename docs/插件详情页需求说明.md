# 插件详情页需求说明（插件仓库侧改造）

> 本文档描述"插件管理器详情页"功能需要在 **xTestPlatform-PluginDev** 仓库中完成的改造。
> 管理器 UI 侧的改动在 xTestPlatform 主仓库中另行实施。

## 1. 需求背景

插件管理器目前列表仅显示：名称、描述、版本、作者/公司、发布时间。
需要为每个插件增加**详情页**，展示三部分内容：

| Tab | 内容 | 数据来源 |
|-----|------|----------|
| 功能介绍 | 插件的详细功能说明（Markdown 渲染） | 插件目录下 `README.md` |
| 包含的步骤 | 该插件提供的所有 Step 的名称与描述 | CI 构建时从 DLL 反射提取，写入 manifest 的 `steps[]` |
| 更新记录 | 各版本变更说明（Markdown 渲染） | 插件目录下 `CHANGELOG.md` |

内容分发策略：**全部打进 manifest.json**（一次拉取全有），插件数量不多时简单可靠。

## 2. 插件目录新增文件约定

每个插件顶层目录（如 `CAN\`、`Modbus\`）下新增两个文件：

### 2.1 README.md（功能介绍，必备）

```markdown
# CAN 插件

## 功能概述
通过 CAN 总线收发报文，支持标准帧与扩展帧……

## 支持的硬件
- Vector VN1630
- PEAK PCAN-USB

## 使用前提
需安装 XL Driver Library ……
```

要求：
- 面向**使用者**（测试工程师）而非开发者
- 首行为 `# <插件名>` 一级标题
- 说明功能、支持的硬件/协议、使用前提、注意事项
- UTF-8 编码

### 2.2 CHANGELOG.md（更新记录，推荐手写，缺失时 CI 自动兜底）

```markdown
# 更新记录

## v0.0.40 - 2026-02-11
- 新增：支持 CAN FD 帧收发
- 修复：波特率 250k 时初始化失败

## v0.0.39 - 2026-02-01
- 首次发布
```

要求：
- 版本号与 csproj `<Version>`（即 Release tag）一致，倒序排列（最新在上）
- 每个版本条目使用 `## v<版本号> - <日期>` 二级标题
- 变更条目以 `新增：`/`修复：`/`变更：`/`移除：` 开头

#### 生成策略：手写为主 + git log 自动兜底（混合方案）

| 方式 | 优点 | 缺点 |
|------|------|------|
| 手写 CHANGELOG.md | 内容面向用户、质量可控 | 依赖开发人员自觉，容易遗漏 |
| git log 自动生成 | 零维护 | 提交消息面向开发者、噪音大、质量参差不齐 |

CI 采用混合逻辑：

1. 插件目录存在 `CHANGELOG.md` → 直接使用手写内容（优先）
2. 不存在 → 用该插件目录的 git 提交记录自动生成本版本段落，并在 CI 输出警告提醒补写

配套约束：为保证兜底内容可读，提交消息应遵循规范——`feat: `/`fix: `/`refactor: ` 前缀 + 面向用户可读的描述（如 `feat: CAN 插件支持 CAN FD 帧`），避免“改bug”、“临时提交”这类消息。

## 3. manifest.json 扩展

在 CI（`.github/workflows/release.yml` 步骤 7"打包 ZIP"）生成 manifest 条目时增加三个字段：

```json
{
  "name": "CAN",
  "version": "0.0.40",
  "description": "…",
  "author": "…",
  "publishedAt": "…",
  "downloadUrl": "…",
  "sha256": "…",
  "size": 12345,
  "minPlatformVersion": "",
  "readme": "# CAN 插件\n\n## 功能概述\n……",
  "changelog": "# 更新记录\n\n## v0.0.40 ……",
  "steps": [
	{ "displayName": "CAN_Send", "description": "发送一帧 CAN 报文" },
	{ "displayName": "CAN_Receive", "description": "接收并匹配 CAN 报文" }
  ]
}
```

### 3.1 readme / changelog 提取（PowerShell，含混合兜底逻辑）

```powershell
# 在 foreach ($dir in Get-ChildItem $publishRoot -Directory) 循环内追加：
$readme = ""
$changelog = ""
$readmePath = Join-Path "$env:GITHUB_WORKSPACE\$pluginName" "README.md"
$changelogPath = Join-Path "$env:GITHUB_WORKSPACE\$pluginName" "CHANGELOG.md"
if (Test-Path $readmePath) { $readme = Get-Content $readmePath -Raw -Encoding UTF8 }

if (Test-Path $changelogPath) {
    # 优先：手写 CHANGELOG
    $changelog = Get-Content $changelogPath -Raw -Encoding UTF8
} else {
    # 兜底：用该插件目录的提交记录自动生成本版本段落
    $prevTag = "${{ steps.bump_version.outputs.prev_tag }}"
    if ($prevTag) {
        $log = git log "$prevTag..HEAD" --pretty=format:"- %s" --no-merges -- "$pluginName/"
    } else {
        $log = git log --pretty=format:"- %s" --no-merges -- "$pluginName/"
    }
    if ($log) {
        $changelog = "# 更新记录`n`n## v$pluginVersion - $(Get-Date -Format yyyy-MM-dd)`n$($log -join \"`n\")"
        Write-Warning "$pluginName 缺少 CHANGELOG.md，已用提交记录自动生成，请尽快补写"
    }
}
```

并在 `$entries += [ordered]@{ … }` 中增加 `readme`、`changelog` 两个键。

> 注意：
> - 兜底生成只覆盖“上个 tag 到本次发布”区间，无法累积历史版本记录；历史完整性只能靠手写文件维护
> - `ConvertTo-Json -Depth 5` 需确认深度足够（steps 为嵌套数组，建议 `-Depth 6`）

### 3.2 steps[] 提取（反射扫描 DLL）

CI 编译完成后（产物在 `publish\<插件名>\`），对每个插件主 DLL（`*.StepPlugin.dll`）反射提取所有 `IStepPlugin` 实现的 `DisplayName` 与 `Description`。

推荐用一个独立的小工具项目（如 `tools/StepInfoExtractor`，控制台程序）：

- 输入：插件目录路径
- 输出：JSON 数组 `[{ "displayName": "...", "description": "..." }]` 到 stdout
- 实现：`MetadataLoadContext`（推荐，避免加载依赖失败）或 `Assembly.LoadFrom` + try/catch
- 提取规则：所有实现 `IStepPlugin` 的非抽象类，读取其 `DisplayName` 和 `Description` 属性
  （需实例化或读取自定义特性，视 IStepPlugin 的定义而定；若属性为实例属性，
  需要 `Activator.CreateInstance` 后读取，失败的类跳过并输出警告）

CI 中调用：

```powershell
$stepsJson = dotnet run --project tools\StepInfoExtractor -c Release -- "$($dir.FullName)"
$steps = if ($stepsJson) { $stepsJson | ConvertFrom-Json } else { @() }
# $entries += [ordered]@{ …; steps = $steps }
```

> 简化替代方案：若反射提取实现成本高，可先在每个插件目录放 `plugin.json` 手工维护 steps 列表，CI 直接读取合并。后续再切换为自动反射。两种方式 manifest 格式保持一致。

## 4. CI 质量门禁（可选，建议）

在打包步骤前增加检查：缺少 `README.md` 的插件目录输出 ⚠️ 警告（首期不阻断构建，过渡期后改为报错）。`CHANGELOG.md` 缺失时由 3.1 节的混合逻辑自动兜底，仅警告提醒补写，不阻断。

```powershell
foreach ($dir in $pluginDirs) {
	if (-not (Test-Path (Join-Path $dir.FullName "README.md"))) {
		Write-Warning "$($dir.Name) 缺少 README.md，详情页将无功能介绍"
	}
	if (-not (Test-Path (Join-Path $dir.FullName "CHANGELOG.md"))) {
		Write-Warning "$($dir.Name) 缺少 CHANGELOG.md，详情页将无更新记录"
	}
}
```

## 5. 开发手册需要新增的章节

在 `xTestPlatform_StepPlugin_Development_Guide.md` 的 **14.2.1 插件元数据** 之后新增 **14.2.2 插件文档（README / CHANGELOG）**，内容包含：

1. 两个文件的存放位置（插件顶层目录）与用途（插件管理器详情页展示）
2. 第 2 节中的格式模板与编写要求
3. 更新插件时**应同步更新 CHANGELOG.md**（新版本条目）；未更新时 CI 会用提交记录自动兜底生成，但内容质量不如手写，且不含历史版本
4. 提交消息规范：`feat: `/`fix: `/`refactor: ` 前缀 + 面向用户可读的描述，保证兜底生成的 CHANGELOG 可读
5. 「开发交付检查清单」章节中追加两项：
   - [ ] 插件目录包含 README.md（功能介绍，面向使用者）
   - [ ] CHANGELOG.md 已添加本次版本的变更条目

## 6. 管理器侧对接约定（供参考，本仓库无需实施）

- `PluginManifestEntry` 新增 `Readme`、`Changelog`、`Steps` 字段
- 详情页 UI：双击列表行或点击"详情"按钮弹出，三个 Tab（功能介绍 / 包含的步骤 / 更新记录）
- Markdown 渲染使用 `Markdig.Wpf`
- 字段为空时对应 Tab 显示占位文案"该插件未提供××"

## 7. 实施顺序建议

1. 新建 `Directory.Build.props` 检查（已完成，见 14.2.1）
2. 为现有每个插件补 README.md 与 CHANGELOG.md
3. 修改 release.yml：提取 readme/changelog 进 manifest（3.1 节）
4. steps 提取：先用 plugin.json 手工方式或直接跳过，反射工具后续迭代（3.2 节）
5. 更新开发手册（第 5 节）
6. 发布一次 Release 验证 manifest 内容
7. 管理器侧实现详情页 UI（另一仓库）
