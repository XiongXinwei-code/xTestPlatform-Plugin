# 插件说明补充规范：运行期资源表

> 适用范围：**所有会向运行期资源表注册对象的插件**，注册侧与释放侧都要改。
> 执行位置：插件仓库 `D:\xTestPlatform-PluginDev`。
> 关联改动：`xTestCopilot\Services\AiChatService.cs` 的 SystemPrompt 已新增【运行期资源表的作用域】一节。

---

## 一、为什么要改

### 1.1 真实事故

AI 助手为烧录工站生成测试序列时，需要判断「父序列 Setup 里打开的 LIN 连接，子序列能不能直接用」。

它调用 `get_step_description` 查到的 `LIN_Open` 说明，「行为」小节只有一句：

> - 打开后通过 ConnectionName 标识连接，供 Read/Write/Cyclic 步骤使用

**「后续步骤」这个措辞回避了唯一关键的问题：范围到哪为止。** 同一个 Block？同一个序列？跨子序列？文档没说。

于是 AI 在「父序列开、子序列用」和「子序列自己开关」两个方案间反复权衡了 **7 轮**，其中 3 次推理方向是正确的（从「同名重复打开」的现象反推出全局注册表），但没有任何权威文本能把「推对」升级成「确认」。

最终它按不对称风险决策：

> 由于我无法确定，最稳妥的就是让每个连接自包含。这不会有任何风险。

把 LIN 的开关从主序列搬进了**每个测试周期都会调用的子序列**。

### 1.2 实际代价

`LinOpenExecutor` 走的是 `Resources.Set`，而 `ResourceRegistry.Set` 会先 `TryRemove` + `SafeDispose` 旧值再写入。

这意味着**每个测试周期都会销毁并重建一次 NI-XNET 适配器句柄**。循环产线测试下，这是实打实的性能损失和稳定性风险。

而事实上，父子序列共享同一张引擎级资源表，原方案完全可行。

### 1.3 第二个坑：跨插件误推

同一段推理里，AI 还引用了「同名 ConnectionName 重复打开会报错，需先 Close」——**这是从 VISA 的说明推到 LIN 头上的**。

LIN 实际是静默替换，不报错。这个错误前提让它凭空担心「循环里重复打开会冲突」，反过来强化了搬迁的决定。

### 1.4 结论

AI 手上有五类查证渠道，`get_step_description` 是其中之一。它查了，读到的是一句没有边界的话。

**这不是 AI 推理纪律的问题，是插件文档的信息缺口。**

## 二、职责划分

改动分两侧，**不要写重复**：

| 写在哪 | 内容 | 理由 |
|--------|------|------|
| **SystemPrompt**（已完成） | 资源表的层级、父子共享、生命周期、推荐写法 | 平台不变量，全插件唯一。写进插件等于同一句话复制 N 份，改一次要同步 N 处 |
| **插件 Description**（本文档） | 本步骤**是否**注册资源、用哪个字段作标识名、**重复注册/释放的行为** | 各插件实现不同，尤其第三项 |

> ⚠️ 插件里**不要**再写作用域和生命周期，提示词已统一说明。

## 三、改动要求

### 3.1 注册侧插件（Open / Create 等）

在 `Description` 的 `## 行为` 小节补两条：

```markdown
## 行为

- <对象名> 会以 `<字段名>` 为标识名注册到运行期资源表，供后续 <XXX / YYY> 步骤取用
- 用同一个 <字段名> 重复注册时：<按下表判定的行为>
```

**第二条必须逐插件核对自己的 Executor 后再写**，判定方法：

| Executor 中的写入方法 | 实际行为 | 说明该怎么写 |
|---|---|---|
| `Resources.Set(...)` | 静默替换，旧对象被 `Dispose` | 「**静默替换**——旧对象会被自动关闭并释放，再注册新对象，不会报错」 |
| `Resources.TryAdd(...)` + 判返回值抛错 | 报错 | 「已存在同名对象时**报错**，需先调用 <释放步骤> 释放」 |
| `Resources.GetOrAdd(...)` | 复用已有，新建实例被丢弃 | 「已存在同名对象时**直接复用**，不会新建」 |

### 3.2 释放侧插件（Close / 对应清理步骤等）

```markdown
## 行为

- 从运行期资源表中查找 `<字段名>` 对应的对象，<关闭/清理动作> 并从表中移除
- 标识名不存在时<按实际行为：不报错仅记录日志并返回 Passed / 抛出异常>
```

**判定方法**：看 Executor 里 `TryGet` 失败时走哪条路——只打日志照常返回 `Passed`，还是抛异常。

## 四、已核实的样例：LIN

### 4.1 `LinOpenPlugin.cs`

替换现有 `## 行为` 小节：

```markdown
## 行为

- 打开的适配器会以 `ConnectionName` 为标识名注册到运行期资源表，
  供后续 LIN_Read / LIN_Write / LIN_Cyclic / LIN_Close 步骤取用
- 用同一个 ConnectionName 重复打开时：**静默替换**——
  旧适配器会被自动关闭并释放，再注册新适配器，不会报错
```

**依据**：`LinOpenExecutor.cs` 调用 `context.Resources.Set(key, adapter)`；`ResourceRegistry.Set` 为 `TryRemove` + `SafeDispose` 后写入。源码原注释即为「Set 会自动销毁同名旧适配器（如上次运行异常终止未关闭）」。

### 4.2 `LinClosePlugin.cs`

替换现有 `## 行为` 小节（原文「关闭后该连接名不可再被其他 LIN 步骤使用」是对的但不完整，未说明重复关闭或关闭不存在连接的后果）：

```markdown
## 行为

- 从运行期资源表中查找 `ConnectionName` 对应的适配器，关闭硬件通道并从表中移除
- 连接名不存在时**不报错**，仅记录日志并按 Passed 返回
```

**依据**：`LinCloseExecutor.cs` 中 `TryGet` 失败走 `else` 分支仅调 `LogAction`，随后照常返回 `TestStatus.Passed`。

## 六、验收标准

改完后，对任意一个注册侧插件调用 `get_step_description`，应能直接回答下列问题而无需推断：

1. 这个步骤会不会往资源表里放东西？
2. 放进去的东西用哪个字段作标识名？
3. 同一个标识名再注册一次会发生什么？

对应的释放侧插件应能回答：

4. 标识名不存在时会报错还是静默通过？

作用域与生命周期问题（子序列能否取用、何时释放）由 SystemPrompt 统一回答，插件无需涉及。
